# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

construct3-chef mutates Construct 3 projects, which store their data as JSON files on disk (`eventSheets/`, `layouts/`, `objectTypes/`, `scripts/`). It exposes the same library two ways: a yargs **CLI** (`src/cli.ts`) and an **MCP server** (`src/mcp/server.ts`). Both are thin wrappers over the pure library in `src/c3/`. When adding a capability, implement it in `src/c3/`, then surface it in both `cli.ts` and `server.ts`. **Known exception — `src/c3/search.ts` is MCP-only** (`server.ts`'s `search` tool + the `src/index.ts` barrel; the CLI never imports it). The CLI's similarly-named `search-dsl` is a *separate, narrower* implementation rooted at `extractedDir`, and `search-docs` is a different capability again (`aceLookup.ts`). Don't infer the surface from the name: this cost real time on [#159](https://github.com/GenvidTechnologies/construct3-chef/issues/159), which was filed `area:cli` with acceptance criteria written as a `search --type json` CLI invocation that does not exist. Check the imports before labelling or scoping work against a `src/c3/` module. Keep the **result rendering** in the `src/c3/` library too (a shared formatter both surfaces call), so the CLI and MCP outputs stay byte-identical instead of drifting — e.g. `aceLookup.ts`'s `formatLookupResult` is rendered once and consumed by the `search-docs` CLI subcommand and MCP tool alike. The **addon tools** follow the same shape: `read-addon`, `validate-addons`, `list-addons`, `diff-addon-aces`, `scan-addon-usage`, and `sync-addon-metadata` are each an off-barrel `src/c3/addon*.ts` module behind a CLI subcommand plus MCP tool(s), each rendering once through a shared `format*` function. Siblings read packages through `src/c3/addonReader.ts`'s `readAddonEntry` rather than re-unzipping (ADR `wiki/decisions/0008`); ACE identity is `(kind, id)`, never `objectClass`, which is the caller-supplied addon name; and `sync-addon-metadata` is the cluster's **only mutation** (ADR `wiki/decisions/0017`). The per-tool design history is in [`wiki/architecture/addon-tooling.md`](wiki/architecture/addon-tooling.md), with the decisions in ADRs 0008–0017 and 0038. That history covers plugin/behavior/effect/expression usage scanning, the UTF-8 BOM strip every addon read depends on, the effect/metadata false-positive fixes, and `--skip-gate`.

## Commands

This repo uses **npm** (committed `package-lock.json`). It's published to npmjs.com as `@genvidtech/construct3-chef` via the `GenvidTechnologies/public-github-actions` GitHub Actions recipe (`.github/workflows/`; formerly `genvid-holdings/genvid-public-ci`); the gate runs `npm ci`. (`@genvidtech/construct3-chef` is the current scope — the package was renamed from `@genvid/construct3-chef` to the GenvidTechnologies org scope and republished starting at `0.11.2`; the old `@genvid/construct3-chef` scope is frozen/deprecated at `0.11.1`. This mirrors the `@genvid/*`→`@genvidtech/*` transfers of the leaf deps `c3source`/`mcp-utils` below.)

```bash
npm install                             # install deps (fetches @genvid/* from npm)
npm test                                # mocha + tsx + chai, all test/**/*.test.ts
npm test -- --grep "foo"                # run tests matching a name (npm needs `--` before forwarded args)
npm run test:file -- test/c3/sidUtils.test.ts   # run a SINGLE file (test:file has no glob, so the path narrows)
npm run lint                            # eslint over src/ AND test/, --max-warnings 0
npm run typecheck                       # tsc --noEmit — checks src/ ONLY (test/ has known type errors; see commit 0b4c515)
npm run build                           # tsc → dist/, then prepends a node shebang to dist/cli.js
```

> **Single-file runs need `test:file`, not `npm test -- <path>`.** The `test` script hardcodes the `'test/**/*.test.ts'` spec glob, and mocha **merges** (doesn't override) a positional path with a config/inline spec — so `npm test -- test/c3/foo.test.ts` silently runs the *whole* suite (the path just dedups against the glob). `test:file` is the same command minus the glob, so the forwarded path is the only spec. `--grep` works on `npm test` because it's a name filter, not a spec.

There is no dev script for the CLI. Run it in-place with `npx tsx src/cli.ts <subcommand> --project-dir <path>` — tsx compiles the `.ts` on the fly, so no build is needed. The package's `main`/`types`/`exports` point at the built `dist/` (what published consumers import); the `construct3-chef` bin also only exists after `npm run build` (it points at `dist/cli.js`).

> **Probing an internal `src/c3/` function ad-hoc** (not the CLI): write a temp `.mts` file at the repo root and run `npx tsx that-file.mts` (delete it after). Do **not** use `npx tsx -e "<import … from './src/…'; …>"` — the inline-eval form with multi-line ESM imports silently yields no output in this repo's `NodeNext`/`"type":"module"` setup, so it's not usable for quick probes.
>
> **The repo root is only for probes that import `src/`.** A probe that needs no repo import — a `node:fs` behavior check, a question about a dependency's actual semantics — belongs in the **scratchpad**, not the tree, so it can't be committed by accident and needs no cleanup step to remember. Three traps in getting one to run there: the Bash tool's `$TMPDIR` is **unset** on this machine (a `> "$TMPDIR/probe.mjs"` heredoc writes to `/probe.mjs` → `Permission denied`), so use the session scratchpad's absolute path; **`/tmp` is not a shared location either, and this one fails silently across tools** — the Bash tool resolves `/tmp` to `C:\Users\FABIEN~1\AppData\Local\Temp`, while a *Windows* `node`/`npx` process resolves the same string to `C:\tmp`, so a file written by a bash redirect (`… > /tmp/x.txt`, which succeeds) and read back by `node -e 'readFileSync("/tmp/x.txt")'` fails `ENOENT` on a path that looks entirely plausible in the error message; the same absolute-scratchpad-path rule fixes it, but the `$TMPDIR` reasoning above does **not** cover it — a reader who knows only that `$TMPDIR` is unset may reasonably conclude `/tmp` is the safe substitute, which is exactly the trap; and the scratchpad has **no `node_modules`**, so a bare `import { walkFiles } from "@genvidtech/mcp-utils"` fails `ERR_MODULE_NOT_FOUND` — import the installed copy by absolute path instead (`import { … } from "file:///C:/repos/construct3-chef/node_modules/@genvidtech/mcp-utils/dist/walkFiles.js"`). Reach for this whenever a plan or an issue turns on *"what does this primitive actually do?"*: #160's proposed fix cited `walkFiles` as precedent for a predicate it doesn't implement, and a ten-line scratchpad probe settled it in one run where reading the issue would have shipped a new defect.

### Releasing

Cutting a release is a tag push, not a manual `npm publish` — and the **`gvt-dev:release-npm-package`** skill owns the procedure; run it rather than working these notes by hand. What follows is deliberately **not** a second copy of its runbook, but the repo-specific facts and overrides it cannot infer. **Where this section and the skill disagree, this section wins — and nothing enforces that**: the skill reads this file for the commit-message format alone, so every other override below is on whoever runs it to apply. The overrides:

1. **Always a topic branch → PR → squash-merge to `main`, whatever the branch-protection status.** `main` carries none, and the skill's runbook branches on protection status, so left to itself it would push the release commit straight to `main` — which § Branching forbids. Bump `package.json` `version` on that branch; the release commit subject is `chore: release X.Y.Z`, lowercase per § Commit Format (the skill's built-in fallback capitalizes `Release`, and this file is what overrides it).
2. **Move the `CHANGELOG.md` `[Unreleased]` entries into a dated `## [X.Y.Z]` section in the same release commit.** PRs accrue entries under `[Unreleased]` via the `Changelog Notice` check (§ Commit Format) — not all of them, since it is advisory and exempts `docs`/`style`/`test`/`chore` touching no `src/` — and the release is what converts whatever accumulated, with no CI step verifying it happened. The skill performs the move and its precondition does require a dated section for the version being released — but that section is created *by the move itself*, so an empty `[Unreleased]` yields an empty dated section that satisfies the check ([gvt-dev#515](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev/issues/515)) — so read the diff before committing.
3. **Tag the *merged* commit**, never the topic branch's — the tag is what the publish job checks out, so tagging a pre-squash commit publishes from a commit that never landed on `main`. ⚠️ **The version check below will not catch that**, because the pre-squash commit already carries the bump and the check compares only the tag against `package.json` at the tagged commit — it never asks whether that commit is on `main`. This repo's `v*` tags are annotated; the skill detects the convention rather than assuming one.
4. **After the publish run succeeds, request the downstream pin bump.** This package's MCP server is made for the `gvt-construct3` plugin, which pins an *exact* version (`@genvidtech/construct3-chef@X.Y.Z` as an `npx` arg in its `plugin/.claude-plugin/plugin.json` `mcpServers`) — so a release does nothing for plugin consumers until that pin moves. File an issue on [`GenvidTechnologies/claude-code-plugin-gvt-construct3`](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-construct3/issues) asking to bump the pin to the new version, **including a summary of the release's changes** (e.g. `git log <prev-tag>..<new-tag> --pretty='- %s'`), and asking them to re-run their `docs/tool-surface-reconciliation.md` step if anything a consumer addresses by name moved — a **resource** counts as much as a tool, despite the step's name ([#207](https://github.com/GenvidTechnologies/construct3-chef/issues/207) changed no tool but repathed every `docs:///` resource, which the plugin had to act on in [gvt-construct3#87](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-construct3/issues/87)). See [gvt-construct3#8](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-construct3/issues/8) for the template. That issue is the trigger for the downstream `gvt-dev:reconcile-mcp-pin` skill, not a request for a hand-edit.

The `v*.*.*` tag triggers `.github/workflows/publish.yml`: the gate job runs the shared `node-gate.yml` recipe — `npm ci` + lint/typecheck/test/build — then the publish job runs `npm ci`, `npm run build`, the tag check, and `npm publish --provenance --access public` via OIDC trusted publishing (no stored npm token). **The publish job fails the "Verify tag matches package version" step if the tag minus its `v` ≠ `package.json` version** — so always tag the commit that already carries the bump (don't tag `main` before the bump merges). ⚠️ **No packaging check guards either path**: the dry-run step never runs on the tag path, because `publish.yml` calls the shared gate with no inputs while `ci.yml` passes `dry-run: true` — and even on a PR that step is `continue-on-error`, so it cannot fail a gate there either. (Cautionary precedent: `0.2.0` was merged to `main` but never tagged, so it was never published — the tag push, not the merge, is what publishes.)

## Leaf dependencies

`@genvidtech/c3source` and `@genvidtech/mcp-utils` are public packages on npm; `npm install` fetches them from the registry like any other dependency. Versions are pinned in `package.json`. (`@genvidtech/c3source` is the current scope — the package was transferred from `@genvid/c3source` to the GenvidTechnologies org and republished starting at `^1.6.0`; the old `@genvid/c3source` scope is frozen/deprecated at 1.5.0. `@genvidtech/mcp-utils` is likewise the current scope — the package was transferred from `@genvid/mcp-utils` to the GenvidTechnologies org and republished at `^0.5.1` (API-identical to the now-frozen `@genvid/mcp-utils@0.5.0`; closes #104). These packages were once private tarballs pulled from Azure Blob via a `download-deps` + 1Password bootstrap; that machinery was retired when the packages went public — `git log` for the history.)

> **Checking for a new upstream release:** use `npm view <pkg> version --prefer-online` (or check the package's GitHub tags). Plain `npm view` and the editor's "new version available" banner both read a *cached* registry index and lag fresh publishes — don't conclude you're current off the cached read when deciding whether to adopt.

- **`@genvidtech/c3source`** — the C3 JSON domain layer: type definitions (`EventSheet`, `Condition`, `Layout`, …), file discovery (`find_all_eventsheets_path`), and primitives like `extractScriptsFromSheet`, `formatCondition`. Treat it as the source of truth for C3's on-disk schema.
- **`@genvidtech/mcp-utils`** — MCP plumbing: `ReadWriteLock`, `ExpectedChanges`, `paginateText`, `exposeDocs`, `Logger`.

**Adoption posture (the recurring "should this live upstream?" call).** Push **traversal, numbering, and discovery** into c3source — that's domain logic (`visitEvents`/`visitLayers`, the `isCountingEvent` event counter, the `find_all_*_path` finders). Keep **rendering/presentation** local — the `extracted/` read-surface (DSL text, index, layout summaries) is *this tool's* invention, not C3 on-disk schema, so it must not move upstream even when a c3source helper could shave a few lines. The split was settled in #27 (the DSL formatter drives traversal via `visitEvents` but renders locally) and guides the remaining adoption issues (#25/#26/#28). When a needed traversal/discovery primitive is missing upstream (e.g. #28 wanted a `.dsl.txt` file finder that c3source doesn't export), file an intent request on `GenvidTechnologies/c3source` rather than re-rolling it here. **Owning the *fact* upstream isn't sufficient — check the primitive's *shape* fits the consuming *operation*.** **⚠️ After adopting an upstream *behavior* change, revert-confirm the local guards that overlap it — a green suite post-bump does not mean your guards still guard.** When upstream starts doing what a local clause was doing, the local clause's tests can keep passing **for a different reason**, silently converting a guarded clause into an unguarded one with no diff, no failing test, and no actor to notice. This is distinct from the "does the bump change our output?" question the per-version entries in `wiki/process/leaf-dependency-ledger.md` answer: nothing about the *product* changed, only what the *test* was proving. **So: for each local guard the upstream change overlaps, delete it and confirm a test still fails; if none does, the coverage is now vacuous and the guard needs a test written at the surface upstream does *not* reach.** Related: a `^0.x.y` range **excludes** the next minor (`^0.5.1` = `>=0.5.1 <0.6.0-0`), so a 0.x bump is real dependency work, not the adoption-without-a-bump shape the c3source entries in `wiki/process/leaf-dependency-ledger.md` describe. Both rules above are stated here without their cases: the #42 / c3source#21 shape-fit precedent (also ADR [`0006`](./wiki/decisions/0006-upstream-ownership-boundary-and-adoption-posture.md), which names it the canonical "request the right shape, wait" precedent) and the #168 / mcp-utils 0.6.0 revert-confirm case both live in `wiki/process/leaf-dependency-ledger.md` under their version entries.

The same posture governs **`@genvidtech/mcp-utils`**: generic MCP/config *plumbing* goes upstream, the project-specific schema and behavior stay local. **The version-by-version record — what each upstream release shipped, what chef adopted, and the deliberate declines that must not be re-litigated — lives in [`wiki/process/leaf-dependency-ledger.md`](./wiki/process/leaf-dependency-ledger.md), one section per package, oldest entry first.** Routing test for a new version fact: if it would need editing when the next version ships, it belongs in the ledger; if it survives every version, it belongs here. Before adopting a new upstream release, read that package's newest ledger entry — the declines are recorded there rather than silently skipped, and the newest entry names what to check at the next bump.

## Module system gotchas

ESM throughout (`"type": "module"`, `NodeNext`). **Relative imports must use the `.js` extension even though the files are `.ts`** (e.g. `import { foo } from "./generators.js"`). `strict` is on. Two tsconfigs: `tsconfig.json` (src-only, emits to `dist/`, used by build + typecheck) and `tsconfig.test.json` (adds `test/`, `noEmit` — exists for editors, not wired into the `typecheck` script).

**Public-API surface = the `src/index.ts` barrel.** It re-exports each module wholesale (`export * from "./c3/dslFormatter.js"`, …), so *every exported symbol* a module declares becomes published API the moment it ships in `dist/`. Deleting or renaming an exported function/type/interface is therefore **semver-breaking** even when nothing inside the repo still imports it (e.g. #27 removed the unused-internally `formatEvent`/`EventCounter` — breaking for any consumer importing them from `@genvidtech/construct3-chef`). Since `1.0.0` this is no longer a cheap change: a removal or rename requires a **major** bump, so prefer deprecating a symbol (keep it re-exported, document the replacement) over deleting it, and note any unavoidable removal in the commit body plus at the release tag (see [Releasing](#releasing)). (Pre-`1.0.0` such removals were absorbed by a minor — e.g. #27's `formatEvent`/`EventCounter`, and the `readDiskDirNames`/`syncNameFolder` removals.) To keep a symbol internal, don't re-export its module from `src/index.ts`.

## The two-surface data model

This is the central idea. There are two views of the project — plus a third artifact that is neither, described at the end of this section:

- **Source JSON** (`eventSheets/`, `layouts/`, `objectTypes/`) — the write surface. The actual C3 project. Never hand-edit blindly; mutate via recipes.
- **`extracted/`** (DSL `.dsl.txt`, index `.dsl.idx.txt`, TypeScript `.ts`, layout summaries, `template-scope.txt`, `sid-registry.txt`) — the read surface. Human/AI-readable, regenerated from source by the 6 generators in `src/c3/generators.ts`. Committed alongside source for diffing. The directory name defaults to `extracted/` but is configurable via `extractedDir` in an optional `construct3-chef.config.json` at the project root (loaded by `src/c3/chefConfig.ts`'s `loadChefConfig` over mcp-utils' `loadProjectConfig`; the value is path-contained to the project root). The same config file also carries `navigation` (nav convention overrides) and `ops` (`ops.dir` / `ops.watch` for user-defined ops). The source-JSON dir names are C3-fixed and stay hardcoded. See `wiki/reference/cli.md` § Configuration file and `wiki/reference/ops.md`.

**The MCP docs resource serves `wiki/` directly** — `server.ts` calls `exposeDocs(server, __pkgDir, { docsDir: "wiki", recursive: true })`, so every tracked `*.md` under `wiki/` is served at its real relative path (`docs:///reference/cli`), enumerable via `resources/list`, identically from a source checkout or an installed package (ADR [`0033`](./wiki/decisions/0033-mcp-docs-resource-serves-wiki-directly.md), superseding the generated flat-`docs/` workaround of ADR [`0029`](./wiki/decisions/0029-flat-docs-alias-generated-into-the-tarball.md)). `.gitignore` still ignores `/docs/`, deliberately, as insurance against an accidental commit recreating the retired tier. ⚠️ **Anything wired into `prepack` must write its diagnostics to `stderr`, never `stdout`** — `npm pack --json` merges the script's stdout into its own output, so a single `console.log` renders the manifest unparseable and silently breaks every consumer of it, including this repo's own pack assertions.

> **Adding a generator touches ~9 sites in lockstep.** `GENERATORS` in `src/c3/generators.ts` is now the single source of truth (#178, ADR `wiki/decisions/0022`): `cli.ts`'s `runGenerators` filters it directly by `--only`, and `server.ts`'s `GENERATOR_STEPS` is `.map()`-derived from it, so the old private `GENERATOR_NAMES` + `generators` array in `cli.ts` no longer exist as separate drift sites and `GENERATOR_STEPS` itself no longer needs manual editing. The rest are a hardcoded count that still silently drifts if missed: the four `totalSteps`/`progressTotal` constants in `server.ts` (the `runGenerators` default and the apply-recipe / clone-layout / workflow tool handlers — each is "N + generators", so all bump by one) and the `regenerate` tool's description string; the golden test's `before` hook (`test/c3/sampleProjectGolden.test.ts`); `EXPECTED_TRACKED_FILES` in `scripts/verify-fixture-parity.mjs` (a new generator adds a golden file, so the tracked-overlay count moves); plus `wiki/reference/generators.md` / `wiki/reference/cli.md` / `wiki/index.md` / `wiki/architecture/mcp-architecture.md` and the count in this file. Grep `totalSteps`/`progressTotal` in `server.ts` after wiring a new one. `test/c3/generatorOutDir.test.ts` is deliberately NOT one of these sites — it iterates `GENERATORS`, so a seventh entry gets outDir-self-sufficiency coverage automatically with no edit to that file. `README.md`'s MCP `regenerate` row is likewise NOT one, for the same mechanical reason but only since [#199](https://github.com/GenvidTechnologies/construct3-chef/issues/199) — and it is worth knowing *why* it was exempted, because it earned its place the hard way: that row is a generator-count site (it reads "Run all N generators") which this enumeration never named, and it had drifted to **5** against six, unnoticed, precisely because nothing listed it. `test/readmeCommandInventory.test.ts` now asserts the row's count against `GENERATORS.length` instead, so the count is derived rather than restated — the same fix the "name the items, let the count fall out" rule in § "Conventions" prescribes for prose, applied to a doc by a test. The lesson generalizes past this row: a site absent from a lockstep list is not thereby safe, it is merely unwatched, so when a count in prose turns out to have drifted, check whether the enumeration that should have caught it names that site at all. (Cf. the objectType lockstep note below.)

Workflow loop: **read `extracted/` to locate a target → write a recipe targeting it by SID → apply to source JSON → regenerate `extracted/` → sync `project.c3proj`.** After any source mutation, `extracted/` is stale until regenerated.

### SIDs are the addressing system

C3 nodes carry a stable `sid` (a random integer in `[1e14, 1e15)`). Recipes target nodes by SID (`"in": "sid:123…"`) rather than fragile JSON paths — you discover SIDs from the `.dsl.idx.txt` index or via the `resolve-anchor` MCP tool. `src/c3/sidUtils.ts`'s `mintUniqueSid(usedSids: Set<number>)` is the canonical SID minter: stateless, it mints one fresh SID against a caller-owned `Set` of already-used SIDs (mutating that Set by adding the new SID before returning), throwing after 100 collision attempts. Callers seed `usedSids` from `sid-registry.txt` via `readRegistryFile` (or wrap it in a closure via `freshSidGen()`/`makeSidGen(used)` for a `() => number` generator shape); there is no module-level context to initialize or reset.

## Recipe pipeline

- **`recipeInterpreter.ts`** — declares the `Recipe` type (`objectTypes`, `addInstVars`, `files`, `layouts`), all the op shorthands, `validateRecipe`, and the **pure** execution functions (`executeRecipe`, `executeFileOps`, `applyReplacements`) that transform in-memory `EventSheet` objects with no I/O.
- **`recipeApplier.ts`** — the orchestrator with I/O. `applyRecipeInner` applies in a fixed order: **objectTypes → addInstVars → layouts → files**, then writes files and regenerates. Adding an objectType touches three places in lockstep: the `objectTypes/*.json`, `scripts/ts-defs/instanceTypes.d.ts`, and `scripts/ts-defs/objects.d.ts`. Layout ops dispatch into `layoutMutator.ts`.
  - **Two validation chokepoints guard every event-sheet write** (both fire in `validate-recipe` dry-run *and* `apply-recipe`, before any disk write): (1) `assertEditorValid` (c3source `validateForEditor`) — **editor-load** validity, the per-sheet check that the C3 editor will accept the project on import (#84); (2) `validateInsertedCustomActions` (`customAceIndex.ts`, off the barrel) — **runtime-resolution** validity, project-context-aware, rejecting a recipe-inserted family-provided custom-action that lacks `customActionObjectClass` (#88). These are *different layers*: a runtime-resolution defect passes editor validation and renders **byte-identical DSL** (`formatAction` never reads `customActionObjectClass`), so it's invisible until C3 runtime — hence the dedicated check. `customAceIndex` enumerates custom-action *definitions* from `custom-ace-block` events (via c3source `extractFunctions`, which carries the owning `objectClass`) + `families/*.json` membership.
- **`workflowExpansion.ts`** — composite **workflow ops** (`extract-template`, `templatize-in-place`, `clone-replica-to-layouts`, `replace-instance-with-replica`) expand into primitive layout ops in a pre-pass before the layout-file loop runs, fanning out across multiple layout keys when needed. Dispatch and dry-run logging iterate the expanded `Map`, so workflows are validated as their primitive sequence.
- **`eventSheetMutator.ts`** — low-level builders (`buildBlock`, `buildAction`, …) and tree edits (`insertEvent`, `resolveNode`, SID-index building) over a single sheet.

> **`SidIndexEntry.indexInParent` is a snapshot, not a live index.** `buildSidIndex` records each node's position once; the `parentArray` reference stays valid but the stored index goes stale the moment an earlier op in the same recipe batch splices that array. Any op that positions relative to a resolved node (insert-after, remove, move) must recompute with `parentArray.indexOf(node)` — never trust `indexInParent` for placement. (This was gotcha #34: the `insert-event` `after: "sid:X"` branch used the stale snapshot and misplaced/appended.)

The recipe reference (all event-sheet + layout ops, SID addressing, builder shorthands) lives in `wiki/reference/recipe-reference.md`; generator internals in `wiki/reference/generators.md`.

## MCP server state model (`src/mcp/server.ts`)

The CLI is stateless; the server hosts N registered C3 project roots (#95) behind a concurrency layer worth understanding before editing it. **The per-project-state rule: a binding is per-project state iff serving a second root concurrently would require a second independent value or instance** — apply this over every top-level declaration in `server.ts`, and over closures (e.g. `txIdLine`) and `startServer` locals (e.g. `opsRegistries`) that capture per-project data, not just scalar bindings.

- **`ProjectContext` / `ProjectRegistry`** — one `ProjectContext` (`src/mcp/projectContext.ts`) per registered project collapses what used to be seven module-level globals; `id`/`root`/`extractedDir`/`project`/`rwlock`/`expected`/`config` are getter-only over `readonly #private` fields, so a piecemeal reassignment throws `TypeError` instead of silently going stale. `ProjectRegistry` (`src/mcp/projectRegistry.ts`) is a launch-fixed `Map<id, ProjectContext>`; `regP` resolves each call's `project` selector against it before dispatch — a pure `Map` lookup, no filesystem access — so a handler body always receives an already-resolved `ctx` rather than reading a module-level default. See ADR `wiki/decisions/0034`. **Chef config is launch-fixed per context** ([#211](https://github.com/GenvidTechnologies/construct3-chef/issues/211), ADR `wiki/decisions/0035`): `ctx.config` is loaded once by `createProjectContext` and every handler resolves from it — never a fresh `loadChefConfig(ctx.root)`, which would additionally drop the `overrides` that factory merges, so the two are not guaranteed to agree even in principle. The per-call direction is structurally unavailable, not merely undesirable: `extractedDir` and `ops.dir` are wired into the watcher and `OpsRegistry` at launch by `wireAllProjects`, so config that *cannot* hot-reload sets the ceiling for config that can. ⚠️ `DEFAULT_CHEF_CONFIG` is **not** a fourth lifetime to unify — its use by `__setProjectRoot`/`__resetTestState` is deliberate and defended by the comment above `__setProjectRoot`, so "unifying" it would change test-harness behaviour rather than production behaviour. The consequence for tests: a seam-built context can never carry a `navigation` block, so any test needing one must go through `createProjectContext` + `__setRegistry` (the T-W1 pattern), not `__setProjectRoot`.
- **`txId`** — each context's own `OptimisticWatcher.txId` counter (`ctx.watcher.txId`, bumped via `ctx.watcher.bump()`), but emitted and accepted on the wire as the composite `<projectId>:<counter>` string (`src/mcp/txToken.ts`'s `formatTxToken`/`parseTxToken`/`compareTxToken`) — a bare per-project integer would make an equal counter across two projects (the common case, since both start at 0) silently acceptable against the wrong one. Read tools / `validate-recipe` return the current token; `apply-recipe` / `sync-project` accept an expected token and reject if it has moved or names a different project.
- **`extractedDirty`** — a mutable field on `ProjectContext`, true when that project's source has changed since its last regenerate; read tools append a stale warning and `checkSourceFreshness` flips it by comparing mtimes.
- **File watchers** — `createSourceWatcher` wires @genvidtech/mcp-utils' `OptimisticWatcher` over one context's source dirs + `project.c3proj`, assigned onto `ctx.watcher` by `setupWatchers`. Watchers are never shared across contexts — `suppress()`'s depth counter is per-instance, so a shared watcher would let one project's self-suppressed write blind another's external-change detection. Self-induced writes are masked by wrapping them in `watcher.suppress(async () => { … })` plus `watcher.expect(absPath)` for paths whose event may land after the window closes. ⚠️ **`startServer` wires the watcher and the ops registry together in ONE per-project loop (`wireAllProjects`) — keep them there.** `ctx.watcher` carries a definite-assignment assertion, so a context that never receives one holds `undefined` and throws on the first `ctx.watcher.txId` read, which is most of the tx-tracked surface (`txIdLine`, `compareTxToken`, `get-state`). Splitting them once broke every non-default project at runtime while the whole suite stayed green ([#95](https://github.com/GenvidTechnologies/construct3-chef/issues/95)); the guard (T-W1) drives the real `wireAllProjects` against contexts deliberately given no watcher. Startup validation and auto-generation do remain default-only, deliberately — a non-default project's `extracted/` may be stale until `regenerate` runs against it. See ADR `wiki/decisions/0034` Consequences.
- **`ReadWriteLock`** — one instance per context (`ctx.rwlock`), acquired in the handler body only, never inside `regP` (`ReadWriteLock` has no owner tracking, so a wrapper-held lock would nest inside the handler's own acquisition and hang). The general rule is exactly one lock acquisition per call, taken in the handler body — `acquireRead`'s write-preferring guard deadlocks a nested read too, not just a nested write. Tools are tagged `READ_ONLY` / `REGENERATE` / `MUTATE` annotations.
- `CancelledError` paths still bump `ctx.watcher.txId` (`ctx.watcher.bump()`) and set `ctx.extractedDirty` because source was already written before regeneration was interrupted.

## Conventions

- C3 JSON is written tab-indented with **no trailing newline** — the file ends at its closing `}`/`]`, matching what the C3 editor itself writes (all 27 files in the pinned canonical fixture end this way). Source writes (`eventSheets/`, `layouts/`, `objectTypes/`) go through the shared, deliberately off-barrel `src/c3/sourceJson.ts`'s `writeSourceJson(filePath, value)` so the invariant lives in one place instead of being re-derived at each call site. `project.c3proj` goes through c3source's `writeProjectManifest`/`serializeProjectManifest`, which already emitted no trailing newline — this makes the two consistent rather than changing the manifest. `extracted/` remains the one exception: it's chef's own read surface, not C3 source, and keeps its trailing newline (still byte-diffed by the golden test). This **reverses** the previously-documented two-form rule, where event-sheet/layout writes used to append `+ "\n"`; see ADR `wiki/decisions/0030` and #195.
- Prettier: 120 cols, spaces for `.ts`, **tabs** for `.json`. ESLint extends prettier and disables `no-unused-vars` / `no-explicit-any`.
- **Formatting IS gated by `npm run lint`** (as of #54). `lint` runs ESLint *and then* `npm run format:check` (`prettier --check "src/**/*.ts" "test/**/*.ts" "*.json" ".*.json"`), so Prettier conformance is enforced wherever lint runs (incl. the shared `public-github-actions` gate). **Those last two globs are load-bearing and easy to miss: root-level JSON is gated too** — `package.json`, `tsconfig.json`, `.gvt-agent.json`, `.prettierrc` — added by `2302c69`, so hand-editing one with the wrong indentation fails `lint`, not just a `.ts` file. ESLint itself still extends `eslint-config-prettier`, which only *disables* ESLint's formatting rules — it never runs Prettier — so the `format:check` step is what actually enforces it. The whole repo conforms; run `npm run format` (`prettier --write`) to fix drift before committing. **`test/fixtures/` is `.prettierignore`'d wholesale** — it's real C3-export data (the SDK runtime/plugin `*.d.ts`, fixture scripts) plus the generated `extracted/` read-surface the golden test diffs byte-for-byte; never reformat it. (Pre-#54 history: `projectSync.ts` was whole-file tab-indented and ~21 files had drifted because formatting was ungated; #54 conformed them in one isolated `style:` commit and wired the gate.)
- All file I/O is rooted at a `--project-dir` (defaults to cwd); paths inside recipes/tools are relative to that root. Mutate tools include path-traversal guards — keep them.
- **Editor-local path classification goes through `src/c3/editorLocal.ts`** (off-barrel: `hasEditorLocalSegment` / `isEditorLocalPathUnder`), never a hand-written predicate — re-deriving one dimension of a three-dimension rule is precisely the mistake #146 made and ADR [`0016`](./wiki/decisions/0016-shared-file-walk-adoption-triage.md) corrected ("reachability is not classification"). It applies c3source's `isEditorLocalPath` over path **segments**, which is what covers a `uistate/`/`ts-defs/` *directory* as well as a `Foo.uistate.json` *sibling file* and an exact `tsconfig.json`. **Selection rule:** reach for the c3source named collector (`project.findAll*()` / `find_all_*_path`) when the site owns a project root/`C3Project` handle and can afford to fail loudly on an I/O fault; reach for `walkFiles` + `editorLocal.isEditorLocalPathUnder` when the site's contract is a bare directory, is barrel-exported, or depends on the missing-directory/`ENOENT` degrade — never hand-write the editor-local predicate either way. Anchor the classification at the *base* root a walk starts from, not the walked directory, since a caller-supplied walked dir can itself be editor-local (e.g. `layouts/uistate`). The per-site migrations and the deliberate declines (`generators.findJsonFiles`, `projectSync.readDiskDir`, `discoverAndPlanImageCopies`) are recorded in the ADRs below — read them before "fixing" a declined site. ⚠️ Coverage must be **synthetic temp-dir** — the canonical fixture tracks zero editor-local files at every tag, so a fixture-based assertion passes vacuously. See ADR [`0018`](./wiki/decisions/0018-editor-local-writes-are-not-source-changes.md), ADR [`0019`](./wiki/decisions/0019-two-walk-primitives-one-classification-rule.md), and ADR [`0020`](./wiki/decisions/0020-search-walk-editor-local-anchor.md).
- **A retired plugin/scope name lives in more places than `/gvt-dev:audit-conventions` scans.** Its retired-token check cannot see **user-facing strings in `src/`** — the higher-stakes ones, since they ship to consumers of the published package — and it skips any line containing an `http` URL. So **grep the whole repo, don't trust the audit's count**, and check the tests that assert on a rendered string before editing it. Deliberately excluded: `wiki/decisions/` (an ADR is a historical record) and "formerly …" provenance prose (`genvid-holdings`/`genvid-public-ci`). ⚠️ That exclusion covers a retired token in **prose**, NOT a **link target**: a link through a retired org is repointed (ADR [`0032`](./wiki/decisions/0032-retired-org-link-targets-are-repointed-prose-is-not.md)), and `test/retiredOrgLinks.test.ts` guards the class by matching the URL form. This recurs — `@genvid/*`→`@genvidtech/*`, `genvid-c3`→`gvt-construct3`, `genvid-dev:`→`gvt-dev:`, `.genvid-agent.json`→`.gvt-agent.json`. The sweep precedents are in [`wiki/process/verification-traps.md`](wiki/process/verification-traps.md).
- **Guard tests and verifiers — the rules; the precedents are in [`wiki/process/verification-traps.md`](wiki/process/verification-traps.md).** (1) A row that was never red is proven by **mutating the PRODUCTION code it guards**, never by deleting an assertion — and grep that the mutation landed before reading the run. (2) Read **which half** of a paired assertion went red; an exit code alone proves little (yargs `.strict()` also exits 1). (3) **A red verifier is a hypothesis**: diagnose it before "fixing" an artifact, since a positive control proves the verifier *can* fail, not that *this* failure is the artifact's. (4) **A harness that constructs the state under test** — a `__set*` seam, a hand-built fixture — cannot notice that production never constructs it; add one row that drives the real assembly function. (5) A row can **become a tautology through the very change that makes it pass**: assert the expected disposition per input, and re-run the mutation proof *after* the fix.
- **Citations.** A citation *duplicated across documents* is name-based (a `describe`/`it`/symbol name). `file:line` is only for a single in-code pointer next to the thing it names. A `§N` into an ADR must also say what that section decided. Never cite a gitignored, transient artifact's internal numbering (`plan.md` task letters) from permanent source — cite the issue and acceptance-criterion ids — and after correcting one, grep the tree for the *form*. When a citation turns out dead, re-derive what the sentence claims before choosing a new target: a link checker proves a path exists, never that it is the right document. Precedents in [`wiki/process/verification-traps.md`](wiki/process/verification-traps.md).
- **This file's long-form sections are single *unwrapped physical lines*.** Append in place; never reflow or split one. Verify an edit's structure with `awk 'NR>=X && NR<=Y {printf "L%d [%d chars]\n", NR, length($0)}' CLAUDE.md`. **Counting traps that have produced false findings here:** `grep -c` counts *lines*, not occurrences (use `grep -o … | wc -l`); it also counts a comment naming a symbol's *absence* as a call site (anchor to call position — and never pledge an absence row on a token your own change's comments will name); `wc -c` is bytes while `wc -m`/`awk length` are characters; markdown emphasis inside a phrase defeats a plain-text grep anchor; and a rule illustrated by its own forbidden form matches its own sweep. **For any count in prose or a brief, name the items and let the count fall out** — a cardinality is a fact about the structure you measured (rows, hits, files), never about what it is evidence for. **A grep row proves wording *landed*, never that it is *true*:** when a change's deliverable is a claim about another artifact, add a row that reads that artifact. The full list of traps, each with its precedent, is in [`wiki/process/verification-traps.md`](wiki/process/verification-traps.md).

## Commit Format

Conventional Commits: `<type>: <subject>`, where `type` is one of `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `style`. A breaking change is marked with `!` after the type (`feat!: …`) — the `BREAKING CHANGE:` footer form is not used in this repo. Subject is imperative, lowercase, no trailing period. Body (optional) explains the *why* and any non-obvious *what*, wrapped at ~72 cols. When a commit is authored with Claude Code, end the message with a `Co-Authored-By` trailer:

```
Co-Authored-By: Claude <model> (1M context) <noreply@anthropic.com>
```

**`<model>` is the model that actually authored the commit** — read it off the running session (e.g. `Opus 5`), don't copy the example. The line is an attribution record, so a pinned version is wrong the moment the model changes (it has gone stale twice). Drop the ` (1M context)` qualifier if the session isn't a long-context one.

Squash-merged PRs carry a `(#N)` suffix on the subject (added by the merge), e.g. `feat: composite template workflow ops + MCP tools (#9)`.

A `Changelog Notice` CI check runs on every PR: a change needs a `CHANGELOG.md` entry unless its type is one of `docs`/`style`/`test`/`chore` **and** it touches no `src/` file (a `!` breaking-change marker always gates, regardless of type or files touched). Opt out with a PR-body line `Changelog: none — <reason>` — the reason is mandatory, a bare `Changelog: none` does not satisfy it; squash preserves the PR body, so a waiver stays recoverable via `git log --grep`. Pre-check locally with `node scripts/changelog-notice.mjs --base-ref origin/main --title "$(git log -1 --format=%s)"`. The check is **advisory** — there is no branch protection on `main`, so a red check does not block a merge. See ADR [`0039`](./wiki/decisions/0039-changelog-notice-workflow-deny-list.md) for the deny-list rationale.

## Pull Request Format

Host is **GitHub** (`gh` CLI). PR title follows the same Conventional Commit shape as the squash subject. The body should summarize what changed and why, call out verification done (lint/typecheck/test), and note any follow-ups. When generated with Claude Code, append the `🤖 Generated with [Claude Code](https://claude.com/claude-code)` footer.

**Put `Closes #N` (or `Fixes #N`) in the PR body** for every issue the PR fully resolves — one per issue — so the squash-merge auto-closes them. The `(#N)` *subject* suffix that squash-merging adds is **not** a closing keyword: it only links, it doesn't close. (This is how #19/#20 ended up implemented-but-open — their squash subjects referenced the issues but no body carried `Closes`.) For work that's blocked on or split across other issues, link them in prose instead of `Closes` so they stay open.

**A stacked PR stays a DRAFT until its parent merges.** When PR B is based on PR A's branch rather than on `main`, keep B in draft — GitHub disables the merge button on a draft, so this is a mechanical block on folding B into A's branch, not just a convention. Mark B ready only after A squash-merges, B is rebased with `--onto`, and its base has retargeted to `main` (GitHub retargets it automatically when A's branch is deleted on merge). Marking both ready at once is what makes the fold possible; a gate that unblocks A does not unblock B.

**Whichever way a stack resolves, `Closes #N` must end up on the PR that targets `main`.** Folding B into A's branch is a legitimate shortcut — it collapses the stack into one PR and skips the rebase — but it **silently orphans the keyword**: GitHub only auto-closes on merge to the *default* branch, so a `Closes` in B's body never fires and the issue stays open with no keyword anywhere on the PR that actually lands. Migrate it to A's body when you fold. (Hit on #147/#148: #148 carried `Closes #146`, merged into #147's branch, and #146 stayed open — the #19/#20 failure in a new shape.)

## Branching

Default/base branch is `main`. Do feature work on a topic branch (this repo has used names like `upstream-updates`); never commit directly to `main`. Rebase onto `main` to integrate upstream changes; squash-merge topic branches into `main` via PR. Stacked branches rebase with `--onto` after a parent squash-merges — and their PR stays a **draft** until then (see [Pull Request Format](#pull-request-format)).
