# Canonical sample fixture

`CLAUDE.md` § "Test fixture" keeps the everyday rules: prep is automatic, the golden-regeneration command, and the two vacuity traps. This page holds the full mechanics and the pin-bump protocol, which you only need when changing the fixture itself. ## Materialization

**Fixture materialization.** `test/fixtures/construct3-chef-sample/` is not fully tracked in-tree — it's materialized from the `GenvidTechnologies/construct3-sample` git submodule (`test/fixtures/construct3-sample/`, pinned by gitlink; currently `v0.7.0`). `scripts/prep-fixture.mjs` (`npm run fixture:prep`) self-inits the submodule — `git submodule update --init`, **load-bearing, not redundant**: the shared `public-github-actions/node-gate.yml` gate checks out no submodules by default — then `fs.cpSync`s **two** submodule trees into the fixture dir — its `project/` tree over the root, and its `archive-sources/` tree to `<fixture>/archive-sources/`; it's wired as the `pretest`/`pretest:file` npm hook, so `npm test` / `npm run test:file` materialize it automatically, locally and in CI. Root `.gitignore` ignores the fixture dir wholesale except the **12-file `extracted/` golden read-surface**, re-included by negation — chef tracks only its own rendering, nothing that's canonical-fixture material. `prep-fixture.mjs` is copy-only (never deletes), so stale copies survive indefinitely — leftovers from *earlier* pins, not just files a bump removes — which is why the update protocol below opens with an **unconditional** `git clean -fdX` purge rather than a conditional one. `archive-sources/` **must** land inside the fixture root rather than be referenced in the submodule: `resolveAddonTarget` containment-guards an extracted-addon-dir path with `resolveWithin(projectRoot, …)`, so a `--from` pointing outside the root is rejected — keeping the path at `<fixture>/archive-sources/<id>` is what lets the `scan-addon-usage` blast-radius tests address it unchanged. (#139 moved `archive-sources/` + the addon builder upstream into `construct3-sample`, ending the copy-drift risk of chef keeping its own copy; the canonical repo now also gates every shipped `.c3addon` against its sources.) See ADR `wiki/decisions/0013` for the consumption design (chef as prototype/superset consumer; `construct3-sample`'s own ADR 0001 owns the canonical submodule-mechanism rationale).

## Golden test and what the fixture exercises

**Golden test.** `test/c3/sampleProjectGolden.test.ts` regenerates `extracted/` from the materialized fixture `test/fixtures/construct3-chef-sample/` and diffs it against the committed golden (`…/extracted/`), guarding the generate→`extracted/` pipeline (esp. layout-summary `fullLayerName`/global composition + DSL coordinates). **It does *not* validate that the source fixture loads in C3** — it only diffs the read surface. c3source's parser is lenient (it types e.g. variable `comment` / group `description` as optional), but the C3 editor *requires* them as strings on load. So when hand-authoring fixture event JSON, mirror what `eventSheetMutator.buildVariable`/`buildGroup` emit (or a real export) and verify by importing into C3 — green tests alone are **not** sufficient, though the automated guard now backstops hand-authored fixtures: `test/c3/fixtureLoadValidity.test.ts` runs every fixture event sheet through `validateForEditor` and asserts zero issues, catching a `variable`/`group` missing the required string field at test time (closes #61). (Hit on #58: a fixture variable + group missing `comment`/`description` passed the whole suite but failed C3 load with `expected string`. **Established habit:** when a hand-authored *or* generated fixture fails C3 load, contribute the editor-required field rule to the upstream `EDITOR_FIELD_RULES` table in c3source#33, which shipped as `validateForEditor` in c3source 1.4.0.) The fixture is a real C3 export that deliberately exercises the awkward cases: nested objectType subfolders (`global`/`images`/`tiles`) mirroring the manifest tree, a family, a Sprite with a nested animation subfolder, a Tilemap/TiledBackground with a `tilemapBrushes/` tree, `.ts` scripts, a global layer defined in each of two layouts and overridden by the other (`"global layer"` sourced from Second Layout, `"previously local"` from Main Layout — the first real-data pair sourcing from *different* layouts), `function-block`s both with and without a `functionDescription` (`MyAsyncFunction` is `async` with two parameters; `MyFunction` has neither), a `custom-ace-block` (`NavButton.OnClickAction`) holding a `callFunction` action with a **positional `parameters` array** plus a parameter string carrying expression text (`Functions.CallMapped("mymap", "MyFunction") + Functions.MyFunction`), and a boolean event variable read by a `compare-boolean-eventvar` condition. What it does **not** carry is any `uistate/` directory or `*.uistate.json` file — C3 writes them, but the canonical export excludes them (`construct3-sample`'s own `project/.gitignore`), so the generators' editor-local filtering (`isEditorLocalPath` applied over path segments in `generateSidRegistry`) is exercised only by synthetic temp-dir tests and never by this fixture; a uistate regression test written against the sample fixture passes **vacuously** (a trap `test/mcp/serverHandlers.test.ts` fell into and stayed in until [#149](https://github.com/GenvidTechnologies/construct3-chef/issues/149) closed it, replacing the two vacuous assertions with the seeded synthetic `list-event-sheets`/`list-layouts` dimension tests — see ADR `wiki/decisions/0019`). Object types are flat `<Name>.json` in named subfolders, **not** per-type directories. The custom effect `MyCompany_MyEffect` is applied at three sites — Sprite2 (objectType), TextFamily (family), and Second Layout's layer 1 — via a real editor-authored application (the canonical export was round-tripped through C3 r49500), which **fixed** the earlier incomplete hand-authored application (`effectTypes[]` referenced the effect without the `usedAddons` entry / per-instance `effects` data a real application writes, so the **project** null-pointered on import; #132 item 1, closed by adopting the canonical fixture in #130 — items 2–3, two `validate-addons` false positives, are separate and stay tracked in #132). The three-site application is a **change**, not just a completion, from the retired hand-authored four-site data (which named the effect `"My custom effect"` and included a layout-stack site plus a nested sublayer 1.1.1); the effect-scanner tests were re-baselined to the real editor values, with recursive `subLayers` walk coverage preserved via a synthetic temp-dir test.

⚠️ **The same vacuity trap applies to `construct3-chef.config.json`, and it is wider than the `uistate/` one because it is not fixture-scoped: there is no `construct3-chef.config.json` anywhere in the repository** — not in the fixture, not at the root, nowhere ([#211](https://github.com/GenvidTechnologies/construct3-chef/issues/211) verified this by `find`). So every config-driven code path resolves to its schema default in every test, and any assertion about configured behaviour — `extractedDir`, `navigation`, `ops` — passes without exercising the configuration at all. That is precisely how #211's defect survived: two code paths disagreed about *when* config is loaded, but both resolved to `defaultNavConvention()` under test, so they agreed on the value and nothing went red. Unlike the `uistate/` case there is no "the canonical export excludes it" reason to point at — the file simply has no test that writes one. **When adding or changing config-driven behaviour, write the config file into a synthetic temp dir and build the context through `createProjectContext` + `__setRegistry`; a `__setProjectRoot` seam cannot express it, since it hardcodes `DEFAULT_CHEF_CONFIG` (see § "MCP server state model").** When a generator change *intentionally* alters output, regenerate the golden (materialize the fixture first if you haven't run the test suite recently):
```bash
npm run fixture:prep
npx tsx src/cli.ts generate --project-dir test/fixtures/construct3-chef-sample
```

## Update protocol (bumping the canonical pin)

**Update protocol (bumping the canonical pin).** **Step 0, unconditional:** `git clean -fdX -- test/fixtures/construct3-chef-sample/` → `npm run fixture:prep` → `npm run fixture:verify`, *before* the gitlink moves, so the red state that follows is attributable to the new canonical bytes alone. This is **not** conditional on the bump removing a canonical file: because prep is copy-only, leftovers from earlier pins persist indefinitely — the `v0.3.0`→`v0.7.0` bump found 14 pre-#130 `*.uistate.json` files the canonical repo has never tracked at any tag. `npm run fixture:verify` (`scripts/verify-fixture-parity.mjs`) is the oracle: no `*.uistate.json`, no `uistate/` dirs, exactly 12 tracked overlay files, and a recursive path-set + byte compare of the submodule's `project/` tree against the materialized fixture. (The clean can't eat the golden — `.gitignore` ignores the fixture dir with `/*`, not `/**`, so the `!…/extracted/` negation un-ignores that whole subtree.) Then: bump the submodule gitlink (`cd test/fixtures/construct3-sample && git checkout vX.Y.Z`, commit the gitlink change) → `npm run fixture:prep` → `npm run fixture:verify` again at the new pin (an `only in fixture` path means the bump *removed* a canonical file — clean and re-prep; `only in submodule` or a byte mismatch means prep itself is broken) → regenerate the golden (above) → run the full automated gate (`fixtureLoadValidity`'s `validateForEditor`, `typecheck`, the golden byte-diff) → **manually import the regenerated project into the C3 editor** — the automated gates check event sheets and the read-surface diff, not a whole-project editor load (the #132/#130 precedent: a null-pointering project passed every automated gate) → **then clean + prep + verify AGAIN, because the import itself dirties the fixture**: opening the project makes C3 write editor-local state into it (`*.uistate.json` at several levels plus a `layouts/uistate/` directory), which `git status` can't show and copy-only prep never removes. Re-run `npm run fixture:verify` after the import and expect it to FAIL with `only in fixture` — that is the editor's leftovers, not a defect, and it is almost certainly how the 14 pre-#130 files accumulated. A clean import shows **only** `only in fixture`; a `byte mismatch` or `only in submodule` would mean the editor rewrote canonical bytes, which is a real finding → re-classify any canonical file additions/removals against the 12-file overlay list (a canonical path colliding with an overlay path needs a rename, not a silent overwrite).
