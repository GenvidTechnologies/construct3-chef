# Verification and documentation traps

`CLAUDE.md` is loaded into every session, so it keeps each of these lessons as a one-line rule that can fire mid-task. This page keeps the evidence behind them: which issue produced each rule, what went wrong, and why the obvious fix was insufficient. Read it when a rule's short form leaves you unsure whether it applies. It complements [Local verification practice](/local-verification-practice.md), which covers the mechanics of running the gate.

Inside the moved text, **"this file" means `CLAUDE.md`**, "this bullet" means the original `CLAUDE.md` bullet the section came from, and line references (`L87`, `L124`) are `CLAUDE.md` line numbers at that commit. A `§ "…"` reference names a `CLAUDE.md` section.

## Guard tests: prove by mutation, and the vacuity shapes

**A guard test that was never red must be proven by *mutation*, not by reversion.** The revert-confirm rule in § "Leaf dependencies" ("delete the local guard and confirm a test still fails") answers *"does this row depend on the fix?"* — which is unanswerable for a row that was **green from the start**, the case a behaviour-preserving refactor produces by construction. Ask the other question instead: *can this row fail at all?* Force the system into the state the row forbids and confirm it goes red. Precedent both ways: [#177](https://github.com/GenvidTechnologies/construct3-chef/issues/177)'s R9 stayed green through a full red→green ritual while passing identically **in the exact state it claimed to forbid**, and [#154](https://github.com/GenvidTechnologies/construct3-chef/issues/154)'s R6 mutation (append `"\n"` to the `project.c3proj` write) correctly went 47 passing / 1 failing.

⚠️ **Confirm the mutation actually landed before reading the run** — a mutation that silently no-ops returns **green**, which reads as "the row is vacuous" and sends you to rewrite a test that was fine; grep the mutated expression, then run.

⚠️ **The mutation must target the PRODUCTION code the row guards, never the test itself** — *"delete an assertion and confirm it goes red"* is a plausible-sounding inversion that cannot work, since removing an assertion makes a row weaker rather than failing. [#183](https://github.com/GenvidTechnologies/construct3-chef/issues/183)'s T16 was specified that way by the designer and had to be re-derived as a rendering mutation (`!`→`?` in `reportStrayFiles`), which correctly took 12 rows red — including all eight it claimed to protect. ⚠️ And a **third** vacuity shape that *neither* rule catches, because the row genuinely is red overall: one half of a **paired** assertion passing **for the wrong reason**. #183's T1 asserted `exitCode === 1` for a not-yet-registered CLI flag, and that half **passed** at the committed-red commit — yargs `.strict()` rejects an unknown argument and also exits 1 — so only the paired stdout assertion was ever really red. An exit-code assertion about an unimplemented flag is therefore not evidence on its own; pair it with an assertion on output that only the real feature can produce, and read *which half* went red rather than trusting the row's verdict.

⚠️ **And the mirror of all of them: a check that reports *red* is a hypothesis too.** Every rule above hardens against a check that passes when it shouldn't; none covers one that **fails** when it shouldn't — and that direction is the more expensive one, because a false red sends you to "fix" an artifact that was already correct, which is how a verified-clean artifact acquires a real defect. Both false reds on [#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172) were bugs in the *verifier*, never the artifact: one split the source spans at the anchor strings used to locate entries, but those anchors sit **mid-entry**, so its chunks straddled entry boundaries and could never be contiguous once headings were interleaved — 10 false failures against a byte-exact move; the other extracted an entry body by slicing to the next `###` and so swept up the intervening `## <package>` heading, failing by exactly that heading's length. Neither was distinguishable from a genuine failure by its output alone. So **diagnose a red verifier before acting on it** — binary-search the longest matching prefix and print both sides at the divergence, which names the discrepancy in one run. Note what a positive control does and does not buy here: it proves the verifier *can* fail, not that *this* failure belongs to the artifact. See ADR [`0024`](/decisions/0024-project-c3proj-shared-serializer.md).

⚠️ **And a shape none of the above reaches, because every row genuinely passes and every mutation proof genuinely holds: a test that supplies the missing piece itself cannot notice that production never supplied it.** The rules above all ask whether a *check* is sound; this asks whether the check ever ran against the code that ships. [#95](https://github.com/GenvidTechnologies/construct3-chef/issues/95)'s cross-project suites install `ProjectContext`s through the `__setRegistry` seam and hand each one a fake watcher, so they proved the selector logic exhaustively — two rows mutation-proved, one reproducing a real cross-project write — while never executing `startServer`'s wiring, which assigned a watcher to the default project only. **1721 tests passed over a feature that threw `Cannot read properties of undefined` on first use for every non-default project**, and it surfaced from a *documentation* pass reading `startServer` to describe it, not from any test. The tell is a harness that **constructs** the state under test rather than letting production construct it: a fixture builder, a `__set*` seam, or a hand-built object standing in for what a factory or startup path assembles. Such a harness is often necessary — the fix is not to delete it but to add one row that drives the **real** assembly function (here `__wireAllProjects`, the exact function `startServer` calls) against state deliberately left unset, so the wiring itself is under test rather than assumed. Note the asymmetry that makes this expensive: thoroughness *elsewhere* is what hides it, because a suite that exercises every behaviour of a correctly-built object reads as comprehensive coverage of the subsystem.

⚠️ **And a fifth shape, which the red→green ritual actively conceals: a row can *become* vacuous by the very change that makes it pass.** Every rule above classifies a row by how it behaved *before* the fix — green from the start, red overall but half-green, red in the verifier rather than the artifact. This one is red at baseline for a real reason, goes green for a real reason, and is **unfalsifiable afterwards**, because the assertion restates the implementation instead of the requirement. [#217](https://github.com/GenvidTechnologies/construct3-chef/issues/217)'s R4 asserted *"every id `deriveProjectId` produces that survives `add` satisfies upstream's `isValidProjectId`"* and spelled it `if (accepted) expect(isValidProjectId(id)).to.be.true` — which failed honestly at baseline (`add("al pha")` was accepted) and then, once `add`'s guard **was** `isValidProjectId`, became true by construction and could never fail again. Worse, the conditional meant the two whitespace rows the test names in its own comment as *"the regression vector"* took the reject branch and contributed **zero** assertions, so the row covered least exactly where it claimed to cover most. The tell is structural, not historical: **ask whether the assertion could be derived from reading the implementation** — if restating the guard's own predicate satisfies the row, the row is a tautology wearing a baseline. Two remedies, and prefer the first: assert the **expected disposition per input** (a table of `spec → expected id → admitted?`) so every case carries an assertion regardless of which branch it takes, rather than a conditional that silently excuses the interesting ones; and re-run the mutation proof **after** the fix rather than only before, mutating toward the *plausible regression* (here, swapping the guard back to a local hand-rolled predicate) rather than merely deleting it. Note this is the exact blind spot the mutation rule leaves open by its own framing — it fires on rows that *announce* themselves as green from the start, and R4 did not, so a run can apply that rule diligently to one row and miss this shape in the row beside it.

⚠️ **And a sixth shape, which comes before every rule above: a row can be born unsatisfiable because the command it invokes was never run.** The baseline discipline gets every *counting* row run against the pre-change tree, since such a row carries a number to measure. A row whose verification *invokes* something (a CLI call, a script, an MCP tool) and asserts a *behaviour* has no number, so its command can reach the pledge without ever having executed once. [#254](https://github.com/GenvidTechnologies/construct3-chef/issues/254)'s R11 specified `scaffold-layout --out <existing sheet> --no-regenerate`, and every grep row in the same table had its baseline measured. Yet `--no-regenerate` had never worked on that command: the CLI declares the option under the literal name `no-regenerate`, which yargs reads as negating an unknown `regenerate`, so `.strict()` rejects it with help output and exit 1 before the handler runs ([#261](https://github.com/GenvidTechnologies/construct3-chef/issues/261)). A test written to the row's letter would have been red before the fix for the wrong reason, and would have stayed red after it. The test author caught it, using the brief's standing licence to report a defective criterion rather than bend the test, and the row was amended in the open on the issue. The remedy costs one run: **before pledging any row that invokes a command, execute that command once against a temp copy of the fixture.** You are not checking the expected outcome. You are checking that the invocation parses and reaches the code under test.

## Citations

**A citation *duplicated across documents* is name-based; `file:line` is for a single in-code pointer.** Cite a test or function by its `describe`/`it`/symbol name (`the `list-layouts` editor-local dimension tests`) rather than `foo.test.ts:281-292` whenever the same reference appears in more than one place — prose in `CLAUDE.md`, an issue body, and a code comment all drift independently, and nothing detects it. A `file:line` in a JSDoc *next to the thing it names* is fine and stays: it moves with its neighbour, and this file is dense with them by design. The rule is about **duplication**, not line numbers per se. Evidence: the one line-numbered cross-doc citation this repo ever carried (`serverHandlers.test.ts`) drifted into **three mutually inconsistent values** across the issue, this file, and `includeTree.test.ts` — while every other citation here, already name-based, stayed correct. Fixing a drifted citation by re-anchoring it to fresh line numbers just resets the clock; convert it instead.

**A `§N` section reference into an ADR is governed by the same principle in a weaker form:** `§N` is acceptable — an ADR's sections are numbered in the heading text itself (`### 3. DECLINE — …`), so renumbering is a *visible* edit rather than silent drift — but a **bare** `(§N)` is not, because a reader cannot tell a correct section number from a wrong one without opening the ADR. Name what the section decided alongside the number, or pair each number with the symbol that heading is named after. Evidence: this repo's five citations of ADR 0016's `findJsonFiles` decline were correct at the four that glossed what the section decided (`wiki/decisions/0018`, `wiki/decisions/0019`, `generators.ts`, `spriteScaffold.ts`) and wrong at the fifth — the bullet above — which used a bare section number to cover two declines at once and so silently attributed the `readDiskDir` decline to the `findJsonFiles` section ([#169](https://github.com/GenvidTechnologies/construct3-chef/issues/169)); the failure mode is **opacity, not drift**. When naming an ADR's declines, name them rather than counting them: ADR 0016 has **three** (§2, §3, §4), and a count restated in prose is one more thing to drift. See ADR [`0019`](/decisions/0019-two-walk-primitives-one-classification-rule.md).

⚠️ **And never cite a gitignored, transient artifact's internal numbering from permanent source.** `plan.md` is gitignored by design (§ "MCP server state model" work is planned there and the file is overwritten by the next task), so a comment reading `(#95 F6)` names a task letter in a document that no longer exists and was never committed — it resolves to *nothing* for a later reader, which is strictly worse than the drift the rule above polices, since a drifted `file:line` at least points somewhere. [#95](https://github.com/GenvidTechnologies/construct3-chef/issues/95) accumulated **19** such citations across `src/` and `test/`; the issue number and the acceptance-criterion ids (`T-X4`, `T-W1`) are the durable references and belong there instead. Two things generalize past the specific token. First, the same test applies to any planning-time artifact — a phase name, a session number, a scratch-file heading: **ask whether the thing you are citing will exist for someone reading this line in a year.** Second, the recurrence is the instructive part: the first batch was corrected mid-branch and *later tasks reintroduced the form*, because each implementer saw the convention in the plan it was handed rather than in the tree. That is the "fixing one instance hides its siblings" rule arriving through a new door — after correcting such a citation, grep the whole tree for the *form*, not the instance, and re-grep at the end of the branch rather than trusting the earlier sweep.

⚠️ **And a citation can be wrong in two independent ways at once, where repairing the cheap one entrenches the expensive one.** Everything above polices whether a pointer still *resolves* — drift, opacity, a target that was never committed. A pointer can resolve perfectly and name the **wrong document**, and the two defects are orthogonal: fixing "this link is dead" by repointing it at the nearest plausible file converts a *visible* defect into an *invisible* one, since a resolving link no longer looks like anything to check. [#217](https://github.com/GenvidTechnologies/construct3-chef/issues/217) ran the full sequence inside one session: ADR 0036 was drafted citing `0005-optimistic-concurrency-txid.md`, a link check caught that no such file exists, and it was "fixed" to chef's real `0005-mcp-server-optimistic-concurrency-model.md` — after which a code review found the sentence was describing what **upstream's** docstring cites, which is `mcp-utils`' own `wiki/decisions/0005-tx-token-wire-format.md`, a different repository's record entirely. The issue body had it right; the ADR paraphrased it wrong, and the dead-link repair made the paraphrase *look* verified. The lesson is that a link checker answers *"does this path exist?"* and never *"is this the document the sentence is about?"* — so when a citation turns out dead, **re-derive what the sentence is claiming before choosing a new target**, rather than searching for the nearest filename that matches the number you already wrote. Two smells that this is happening: the repaired target lives in *this* repo while the sentence is about an upstream one (a cross-repo claim silently localized), and the number stays fixed while the slug changes — a number you are preserving across a repoint is a number you inherited rather than derived.

⚠️ **And a probe result is a citation, even when nothing links to it.** An analysis subagent's scratchpad probe can reach shipped prose as a premise with no record behind it. The scratchpad is deleted with the session, so the claim cites evidence nobody can open. [#254](https://github.com/GenvidTechnologies/construct3-chef/issues/254)'s analyst probed c3source's name diff and reported that two same-named objectTypes in different folders are either never registered by sync or cause the existing entry to be repointed. Two hops later, ADR 0044's draft stated this as a decision premise, with the direction of the second half inverted ("at the old one" for "at the new file"). The final review flagged it as resting on an uncaptured probe. Re-running the probe end to end on a temp fixture copy, with real drift detection and then a real `sync-project`, reproduced **only the first half**. The duplicate is silently never registered, while the repoint case never appeared. The ADR now states the measured half and links the recorded evidence. Two things generalize. First, **re-run any probe a decision leans on and post its output on the tracking issue before the prose cites it**. Second, expect a multi-part probe claim to be only partly reproducible, and expect each hop through another author's prose to risk flipping a direction word (old/new, source/target, before/after) while it still reads fluently.

## Counting and grepping, and `CLAUDE.md`'s own format

**`CLAUDE.md`'s own long-form sections are single *unwrapped physical lines*, not wrapped prose** — the "What this is" opener is one such line (12,181 chars as of [#164](https://github.com/GenvidTechnologies/construct3-chef/issues/164)), and re-derive rather than trust that figure: the companion figure this bullet used to quote for the leaf-dependency ledger was stale within two issues, and that ledger's version narrative has since moved out to `wiki/process/leaf-dependency-ledger.md` ([#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172)). Append in place; never reflow one, split it into paragraphs, or let an "add a paragraph" instinct open a new line inside it. The trap is that three line-oriented tools quietly mislead here, which cost real time on #164: `grep -c` counts *lines matched*, not occurrences, so it returns `1` for an entry containing a dozen hits and is worthless as a completeness check (use `grep -o … | wc -l`); `git diff --stat` reports `1 insertion(+), 1 deletion(-)` for a multi-thousand-character append, so it cannot tell an append from a whole-line rewrite — establish that separately (`newLine.startsWith(oldLine)`); and a `file:line` citation into one of these lines addresses ~3k tokens of prose rather than a claim, which is a second reason the name-based-citation rule above is not optional here. Verify an edit's structure with `awk 'NR>=X && NR<=Y {printf "L%d [%d chars]\n", NR, length($0)}' CLAUDE.md`: the line *count* must be unchanged, and only the target line's char count may grow. ⚠️ `grep -o … | wc -l` fixes the *counting* trap but not a **second** one it can't see: a rule bullet that quotes the defective form as its worked example becomes a false positive in every later sweep for that form. **This very bullet is the live instance** — it names `ADR 0016 §3` and `(§2)` just above to illustrate the rule, so a whole-file count of either returns **2** while only L124's is a real citation ([#169](https://github.com/GenvidTechnologies/construct3-chef/issues/169)). Scope such a check to the line (`awk 'NR==X'`) rather than the file, and expect the same shape wherever a convention here is illustrated by the thing it forbids — the retired-token sweeps have it too.

A **fourth** tool trap, this one on *size*: `wc -c` counts **bytes** and `wc -m` counts **characters**, and this file is dense enough in multi-byte glyphs (`§`, `—`, `⚠️`) that the two differ by ~500 — so a size quoted in one unit and compared against a figure measured in the other invents a delta that isn't there (posted wrong on [#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172) before being caught). State the unit, and use whichever one the figure you're comparing against used; `awk length($0)` counts characters, matching the per-line figures quoted throughout this bullet.

A **fifth** trap, and the only one here that isn't about a tool: a count restated in prose encodes an invisible *convention* for what counts as one item, and **the convention drifts even when the value doesn't**. L87's generator-lockstep count moved `~10`→`~9` in [#178](https://github.com/GenvidTechnologies/construct3-chef/issues/178), correctly — but a reviewer re-counting that same enumeration with the four `totalSteps`/`progressTotal` constants expanded individually got **11** and reported a discrepancy; under *that* convention the pre-#178 figure would have been ~14, not ~10. Neither count is wrong, nothing in the line says which convention produced it, and the failure mode is the reverse of drift: a good-faith recount manufactures a false finding and invites someone to "correct" a number that was right. So when a count survives in prose, either name the convention inline (here: the four progress constants are one site, each doc is its own) or drop the number for the name-them-don't-count form the ADR-declines rule above already prefers — and when reviewing one, derive the reviewer's convention before believing the delta.

⚠️ **And the mirror of that, which is worse because the audit trail argues against you: a corrected count can decay back to its original wrong value by a different route.** The fifth trap above is the convention drifting while the value holds; this is the *value* returning while the convention holds. [#198](https://github.com/GenvidTechnologies/construct3-chef/issues/198)'s served-page count went **41 → 40 → 41**: the design derived 41 without accounting for `RESERVED` also excluding `log.md` (defective), it was corrected to 40 against a 45-page corpus, and then committing ADR 0029 grew the corpus to 46 and took it back to 41 (decayed) — the same number as the original mistake, reached by entirely different reasoning. Nothing looks wrong at the end state, and the recorded correction makes the figure read as *more* trustworthy than an uncorrected one. Note the self-reference that caused it: **a record that states a count of the corpus it belongs to invalidates itself the moment it is committed**, so an ADR or wiki page quoting a page count is always off by its own existence. The remedy is the one the seventh trap already prefers — state the **rule** and let the count fall out, keep any quoted figure explicitly as-of, and assert a `≥` threshold with a generated oracle (`gen-docs-alias.mjs --check`) rather than an equality that a new page falsifies.

A **sixth** trap, back on tooling and reaching beyond this file to any *doc-anchored* check: **markdown emphasis inside a phrase defeats a plain-text grep anchor.** `grep -c "does not affect the exit code" wiki/reference/cli.md` returns **0** while the phrase is present three times, because the real text is `does **not** affect the exit code` — the bold sits *inside* the span. The dangerous failure is the quiet one, not the noisy one: you grep for a sentence, get 0, conclude it isn't there, and ship a doc that contradicts the code. It bites hardest on a **survival** row (*"this count must stay 1"*), which reads 0 identically before and after and is therefore unfalsifiable in both directions — the vacuous-guard shape again, arriving through a grep rather than a test. This repo's acceptance rows are routinely doc-anchored greps, so: anchor on a **markup-free span**, and confirm the anchor matches something *today* before trusting the count it returns ([#183](https://github.com/GenvidTechnologies/construct3-chef/issues/183)).

A **seventh** trap, the fifth one's authoring-side inverse: that one is about *re-counting* a number someone else wrote, this is about **handing a count to whoever writes the prose**. A count in a brief is not a fact the author verifies — it is a **slot with a known arity**, and an author who cannot find that many items will invent the balance. On [#172](https://github.com/GenvidTechnologies/construct3-chef/issues/172) a dispatch brief said "the four `record before 'fixing' them` declines"; **two** sites carry that exact phrase, and the ADR that came back duly named four items — `generators.findJsonFiles`, `projectSync.readDiskDir`, `SID_SOURCE_DIRS`, and the `descend` note — of which one sits at such a site, the rest being ADR 0016's declines lifted from a different version's entry. Nothing was wrong with the underlying source; the *number* created the shape and the names were fitted to it. A wrong fact invites a check, a wrong arity invites completion — so **name the items and let the count fall out**, in a brief exactly as in the prose the fifth trap governs. And when a fabricated count is corrected, sweep for its copies before believing it gone: this one had also been restated in a `wiki/index.md` entry description, which survived the fix to the ADR body and surfaced only because an unrelated row's count came out wrong.

An **eighth** trap, and it is the self-example trap above — the one whose live instance is this bullet's own `ADR 0016 §3` citation and whose remedy is `awk 'NR==X'` — reappearing outside this file, in `src/`: **a comment naming a symbol's *absence* is an exact match for that symbol**, so `grep -c` over source systematically **overcounts call sites** wherever the codebase documents where something is deliberately *not* used. Both are mention-counted-as-use; what changes is that a *source* mention has no single line to scope to. (Distinguish the **sixth** trap, markup defeating a plain-text anchor, which runs the opposite direction — a real instance that fails to match. And this is not the substring false-positive a trailing `(` already guards: the token genuinely appears in call form.) Evidence ([#191](https://github.com/GenvidTechnologies/construct3-chef/issues/191)): `grep -c "\.expect(" src/mcp/server.ts` returns **4** against **2** real call sites, because `server.ts` carries two comments reading *"No `watcher.expect()` needed"* — one of which exists precisely to explain why that site is safe without it. So the `awk 'NR==X'` remedy does **not** transfer; anchor the pattern to a call position (`^\s*watcher\.expect(`) or read `grep -n` output instead of trusting `grep -c`. The compounding danger is that **running a grep feels like verification** — it converts *"I should check this"* into *"I checked this"*, which is how this count reached a dispatch brief under the **verified** label, got faithfully rendered into `wiki/process/leaf-dependency-ledger.md` by a tech-writer that had no reason to doubt it, and passed lint, typecheck, and 1570 tests, since nothing examines doc prose. The gap being crossed is between *"the token appears N times"* and *"there are N call sites"*, and only the second is ever the claim — which is the seventh trap's **name the items and let the count fall out** arriving by a different route, and the reason this bullet's own remedy is a named pair of handlers rather than the number two.

⚠️ **The eighth trap has an authoring-side corollary that its measurement framing hides: never *pledge* an absence row on a token your own change's comments will legitimately name.** Everything above is about *running* a grep — it warns that `grep -c` overcounts call sites, and hands you the remedy (anchor to a call position). What it never says is that the same fact makes a whole class of **acceptance criteria** unfalsifiable by construction, and such a row is authored long before anyone runs it. Evidence ([#217](https://github.com/GenvidTechnologies/construct3-chef/issues/217)): a criterion pledged `grep -c 'lastIndexOf\|indexOf(":")\|\.split(' src/mcp/txToken.ts` → **0**, and a *later task in the same plan* then wrote the JSDoc explaining why the renderer must not use those three forms — naming all three, exactly as this trap describes. The row was satisfiable when authored and unsatisfiable by the time it was graded; the remedy it needed was already written one screen above it. Two things generalize. First, **the check that feels like diligence here cannot reach it**: re-deriving a row's *baseline* is backward-looking, so reproducing it says nothing about whether a later task will introduce the token legitimately — a green baseline re-derivation manufactures confidence about a forward question it structurally cannot answer. Second, the forward screen must cover **source comments, not just prose**: the plan's own coherence screen did look ahead, but only at the documentation task, while the falsifying mention came from a *code comment* two tasks earlier. So anchor an absence row to call position **from the start** rather than as a repair, and when screening one, read the whole plan for the comments it will write, not only the docs it will write.

⚠️ **And the seventh trap does not need a hand-off to fire — restating a structure's cardinality as a claim about something else is enough, even when you built the structure yourself one step earlier.** As written above it is framed entirely around *"handing a count to whoever writes the prose"*, which reads as a dispatch-brief hazard and therefore as someone else's problem when you are the only author in the loop. It isn't: on [#217](https://github.com/GenvidTechnologies/construct3-chef/issues/217) the same failure ran end to end inside one turn. A probe produced an 8-row input table, the prose that followed claimed `parseTxToken` produces *"**eight** distinct messages"*, and the **next clause of the same sentence** correctly named **three** — the eight were inputs, several share a message template, and one row (`"alpha:05"`) chef *accepts*, so it yields no message at all and is in fact a case where adopting upstream **fixes** chef rather than losing a diagnostic. The count was not inherited from anyone; it was read off the adjacent table's row count, which is exactly what makes it feel verified. So the operative rule is narrower than "distrust counts in briefs" and wider than its current framing: **a cardinality is a fact about the structure you measured, never about the thing that structure is evidence for** — rows are not messages, hits are not call sites, files are not findings. Crossing that gap silently is the whole failure, and it is cheapest to catch by naming the items when you write the claim, because the mismatch becomes visible the moment the list runs short. And sweep after correcting: this one had already propagated to a **public upstream issue** before it was caught here, so the copies rule above applies across repository boundaries, not just across files in this one.

⚠️ **A ninth trap, and it is the sixth one's exact complement: an anchor that matches *perfectly* over prose that is *false*.** The sixth is a real instance failing to match; this is a match that proves nothing about truth. Both are doc-anchored greps, both read as a clean pass, and they fail on opposite sides of the artifact — which matters because every anti-vacuity rule this file carries polices the *check* rather than the *claim*. A row pinning a markup-free span passes every test above: it can fail, its baseline was measured against the pre-change tree, it is satisfiable alongside the deliverable, its corpus is the one it asserts over, and it is graded at the right moment. What it measures is that the pledged wording **landed** — never that the wording is **true**. Evidence ([#230](https://github.com/GenvidTechnologies/construct3-chef/issues/230)): a row pinned `never the topic branch's`, the phrase survived the edit intact, the row graded green — and the causal clause beside it claimed that a tag anywhere but the squash result fails `publish.yml`'s version check, which traces false, since that step compares only the tag against `package.json` at the tagged commit and never asks whether the commit is on `main`, so tagging the pre-squash branch *passes*. Every row in the checklist was green and the sentence was wrong, in the very commit whose purpose was correcting a different false claim about that same workflow file. **The tell is structural: the change's deliverable is a *claim about another artifact*, and no row reads that artifact.** So when a doc change asserts something about a workflow, a schema, a dependency's behaviour, or a sibling document, pledge a row that checks the claim against its referent — trace the mechanism and assert on what it actually does — alongside the grep proving your sentence is present. A span-pinning row is still worth having; it grades authorship, and authorship is not accuracy.

## Retired names

**A retired plugin/scope name lives in more places than `/gvt-dev:audit-conventions` scans.** Its retired-token check reads the docs root + `CLAUDE.md` + `<wikiDir>/`, minus `excludePaths` (gvt-dev ADR-0041; before 4.19.0 it was `docs/**.md` + `CLAUDE.md` only, which since the consolidation had resolved to `CLAUDE.md` and nothing else here — see § "Where to read more") — so it still structurally cannot see **user-facing strings in `src/`** — and those are the higher-stakes ones, since they ship to consumers of the published package: `aceLookup.ts`'s `formatLookupResult` no-cache note (rendered into CLI *and* MCP output) and the `search-docs` MCP tool `description` in `server.ts` both name a sibling plugin. It also skips any line containing an `http` URL, which hides in-scope hits in link-dense prose (gvt-dev [#232](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev/issues/232); scope widening is [#233](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev/issues/233)). So **grep the whole repo, don't trust the audit's count** — the `genvid-c3`→`gvt-construct3` sweep found 8 sites where the audit reported 6. Before editing a rendered string, check the tests that assert on it (the three `no c3-reference cache` asserts match only the stable prefix — luck, not design). Deliberately excluded: `wiki/decisions/` (an ADR is a historical record) and "formerly …" provenance prose (`genvid-holdings`/`genvid-public-ci`). ⚠️ That exclusion covers a retired token in **prose**, NOT a **link target** — [#203](https://github.com/GenvidTechnologies/construct3-chef/issues/203) found 20 links pointing through the retired `genvid-holdings` org, five of them inside `wiki/decisions/`, and all 20 were repointed: a pointer exists to resolve, and fixing where a citation points changes nothing the record asserts, whereas rewriting `formerly …` prose would make the sentence false. See ADR [`0032`](/decisions/0032-retired-org-link-targets-are-repointed-prose-is-not.md). `test/retiredOrgLinks.test.ts` now guards the class, matching the **URL form** rather than the bare token — which is exactly what keeps its exclusion list empty, since the two `genvid-holdings` mentions on this very line are prose and carry no `github.com/` prefix. It is the complement of the audit's scanner, which skips every line containing `http`; note the audit missed this class for a **second** independent reason the issue did not name — its default deny-list (`genvid:`, `genvid-dev:`, `genvid-c3`) never contained `genvid-holdings` at all, so the upstream fix alone would not have caught it. This recurs — `@genvid/*`→`@genvidtech/*`, `genvid-c3`→`gvt-construct3`, `genvid-dev:`→`gvt-dev:`, `.genvid-agent.json`→`.gvt-agent.json`.

## The conventions audit's reach over the wiki layout

**`wiki/` + `raw/` (the LLM-wiki tier)** — this repo's **only** documentation tier since the `docs/` consolidation of 2026-08-20 (ADR [`0028`](/decisions/0028-documentation-consolidated-into-the-wiki-tier.md)), stood up 2026-08-16 and driven by `/gvt-dev:maintain-wiki`: `raw/` holds immutable captured sources, `wiki/` holds the LLM-maintained OKF v0.2 pages plus `index.md`/`log.md`, and `wiki/wiki-schema.md` is the maintenance contract (page format/frontmatter, create-vs-update lifecycle, `raw/` immutability, staleness policy). **Routing rule: everything documentation-shaped lives under `wiki/`; this file keeps only the always-loaded operating context and routes there for the rest.** The tiers are `wiki/reference/` (CLI, recipes, generators, ops), `wiki/architecture/`, `wiki/process/`, `wiki/decisions/` (the ADRs), and top-level pages for durable knowledge with no other home. What survives the consolidation is the rule that motivated it — **exactly one page owns a given fact**; a second copy, whether here or in another page, is exactly the drift trap § "Conventions" warns about. The first page (`wiki/local-verification-practice.md`) exists precisely because its source was machine-local agent auto-memory, invisible to a fresh clone. Unlike this file the wiki is **not** auto-loaded — reach it with `/gvt-dev:maintain-wiki query`. Mechanical notes: `.gvt-agent.json`'s `wiki` block (`wikiDir`/`rawDir`) must be present or `audit-conventions` reports the Environment pillar as `partial adoption` (its detector counts the config block as a sixth signal alongside the five files/dirs) —

⚠️ **but presence is NOT sufficient, and this repo is the standing counter-example: the block is present, all five files/dirs exist, and the pillar still reads `partial adoption`, permanently.** The stuck signal is the sixth one, `schemaDoc`, which the detector hardcodes as `docs/wiki-schema.md` and joins straight to the repo root — it never consults `paths` at all, so the `docs/wiki-schema.md`→`wiki/wiki-schema.md` override this repo declares (below) is ignored. It is **unfixable from this side**: the only way to satisfy the literal is recreating `docs/`, which the standing rule below forbids. So read that row as advisory-and-known-stuck rather than as a configuration gap to chase — and note the direction this correction runs, because it is the expensive one: the sentence it replaces was a *reassurance* that sent a reader to verify a setting already correct, the same shape as the 4.18.0 warning corrected at the end of this bullet. Tracked in gvt-dev #390, whose scope this bullet used to misdescribe — see the end of this bullet; and `maintain-wiki`'s `lint` verb is **never** invoked by `audit-conventions`, so a clean audit is not a statement about wiki content health. Its statement about doc hygiene was vacuous from the consolidation until **gvt-dev 4.19.0**, which shipped [#389](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev/issues/389) and fixed it on both axes: `paths` keys are now **any declared expectation path** (not just the four convention files), resolved in validate *and* `--fix`; and the three hygiene scanners no longer share one hardcoded `docs/` candidate set. Per gvt-dev **ADR-0041** the scope is now **per-scanner** — all three walk the docs root + `CLAUDE.md`, but only `scanRetiredTokens` additionally walks `<wikiDir>/` (drift there is otherwise unowned, since `maintain-wiki`'s `lint` has no retired-token check, while it *does* already own dead links and orphaned pages, so those two deliberately never widen); `<rawDir>/` is walked by none of them, since it legitimately holds retired tokens and dead links as immutable captured source. This repo's `.gvt-agent.json` now configures that fix — `docs/TOC.md`→`wiki/index.md`, `docs/decisions/`→`wiki/decisions/`, `docs/issue-triage.md`→`wiki/process/issue-triage.md`, `docs/wiki-schema.md`→`wiki/wiki-schema.md` — taking the audit to **0 required errors** and the hygiene scan from 1 file to 17; plus `hygiene.excludePaths: ["wiki/decisions/"]`, restoring the ADR-as-historical-record exclusion that silently stopped matching when the ADRs left `docs/decisions/` (the shipped default still names the old path, and `excludePaths` is *unioned* with it, so naming only the addition is correct). ⚠️ Until 2026-08-21 this bullet asserted the scanners "scan `CLAUDE.md` alone" and that the audit "reports **clean** while scanning essentially nothing" — true at 4.18.0, false now. It is recorded rather than deleted because the vacuous-check shape it named was real, and because a stale *reassurance* about a check's reach is the more expensive direction than a stale warning: it tells you not to bother looking. Still open: the hardcoded `docs/wiki-schema.md` references are gvt-dev [#390](https://github.com/GenvidTechnologies/claude-code-plugin-gvt-dev/issues/390) —

⚠️ **which this bullet previously described as "`maintain-wiki`'s 14 hardcoded references", undercounting it on both axes, and that gloss cost a duplicate issue on 2026-09-15.** #390 was re-scoped and re-counted at 4.19.0 to **25 occurrences across 12 files**, and it is not confined to `maintain-wiki`: two sites are *behavioral*, and one of them is `audit-conventions`' own `practice-detect.mjs` — precisely the stuck-pillar bug described earlier in this bullet. Reading the narrow gloss, I filed gvt-dev #501 against a site #390 already names by line, then closed it as a duplicate. Two things generalize past the instance. First, this repo's standing rule to **check plugin source before filing** covers *source* and says nothing about **searching the plugin's tracker**, which is the cheaper check and the one that would have caught it. Second, and the reason this correction is recorded rather than quietly fixed: **a citation's gloss in this file is what a later reader dedups against**, so a gloss that narrows an issue's scope actively manufactures duplicates — when a nearby sentence already cites an issue covering your area, re-read the *issue*, never the gloss.
