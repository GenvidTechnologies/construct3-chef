# Addon tooling

The design history of construct3-chef's `.c3addon` tool cluster. `CLAUDE.md` § "What this is" keeps the operating rules: the tool list, the shared `readAddonEntry` primitive, `(kind, id)` ACE identity, and the fact that `sync-addon-metadata` is the only mutation. This page keeps the per-issue record of how each tool came to be shaped the way it is. The decisions themselves are ADRs 0008–0017 and 0038. For command usage see [the addon CLI reference](/reference/cli-addons.md).

> **Provenance.** Moved verbatim from `CLAUDE.md` at `b4997ef`[^claude-md] (see ADR [0042](/decisions/0042-claude-md-keeps-rules-the-wiki-keeps-their-history.md)); only paragraph breaks were added. Where the text says "at the time" or names a later change, it is describing history as of that commit, and `package.json` / the code remain the authority for current behaviour.

The **addon read surface** follows the same shape: `src/c3/addonReader.ts` (off-barrel) is the shared `.c3addon` reader — hybrid extracted-dir→zip via `fflate`, exposing the `readAddonEntry` primitive — behind the `read-addon` CLI subcommand + MCP tool, with `formatAddonInfo`/`formatAddonList` rendered once; sibling addon tools (#109–#111, #98) import `readAddonEntry` rather than re-unzipping (see ADR `wiki/decisions/0008`).

The first sibling, `src/c3/addonValidator.ts` (also off-barrel; #107, extended by #108), backs the read-only `validate-addons` CLI subcommand + MCP tool: it consumes `discoverAddons`/`readAddonMetadata` to report bundled-`.c3addon` ↔ `project.c3proj.usedAddons` metadata mismatches, package-integrity failures, and orphan/missing/duplicate package-consistency findings, rendering once through the shared `formatAddonValidation`.

`validate-addons` was then extended (#98, folded into the existing command rather than shipping the `validate-addon` command the issue originally proposed — see ADR `wiki/decisions/0009`) to also cross-check each addon's `aces.json`/editor-`plugin.js` `properties` against every `lang/*.json` locale it ships: `src/c3/addonLangValidator.ts` (off-barrel) runs the per-locale check (gated on lang-file presence, so lang-less addons are unaffected), sourcing ACE param ids via `addonReader.ts`'s `listAddonEntries`/`readAddonEntry` and property ids via `src/c3/addonPropertyExtractor.ts` (off-barrel; a best-effort string-literal scan of `plugin.js`, since properties are JS-declared, not JSON). A new `--addon <id|path>` CLI option / `addon` MCP param (resolved by `addonDiscovery.ts`'s `resolveAddonTarget`, either a discovered addon id or a path to a raw addon source tree) scopes a run to one addon, enabling use against addon-dev repos as well as C3 projects.

Two `validate-addons` **false positives** surfaced by the canonical-fixture editor-import (#130) were later corrected (#132): effect addons are **exempt from the `aces.json` required-entry check** in `checkIntegrity` (`kind !== "effect"` — effects ship no ACEs; `addon.json` stays required for all, `aces.json` for plugin/behavior only), and `checkMetadataMismatch` **dropped the `name` field** (a package's `addon.json` display name legitimately differs from `usedAddons[].name`, the user-assigned *instance* name), keeping `id`/`author`/`version` — the `id` row is the identity anchor. (`validate-addons` had **no severity concept** *at the time* — every finding was CI-failing via `cli.ts` — so the fix was to *drop* the wrong check, not downgrade it. ⚠️ That premise was **relaxed by #220's `--skip-gate`** (ADR `wiki/decisions/0038`, described at the end of this line): selectable fatality now exists, so the "drop, don't downgrade" reasoning recorded here is the *historical* rationale for #132 and no longer binds a future wrong-check decision. #132 item 1, the in-tree fixture's incomplete effect application, was deferred to #130.) The `addon-validate` fixture's `build-archive.mjs` was generalized to **kind-route** archives into `addons/{plugin,effect,behavior}/` and zip each source's actual file set (was plugin-only + a fixed three-file set), preserving byte-identity of the existing packages.

The read-side sibling `src/c3/addonInventory.ts` (off-barrel; #111, capability 7) backs the read-only `list-addons` CLI subcommand + MCP tool: `listAddons` reconciles bundled `.c3addon` packages (flat `discoverAddons`), `project.c3proj.usedAddons`, and editor-only addons (`bundled:false`) into one row per addon id — classified bundled/editor-only/missing/orphan — rendered once via `formatAddonInventory` (it presents the same reconciliation `validate-addons` reports as findings, but as a never-failing inventory; duplicate/nested-package detection stays a `validate-addons` concern). Its prep step extracted the previously-private `readUsedAddons`/`UsedAddonEntry` into a shared off-barrel `src/c3/addonManifest.ts` and promoted `resolveAddonId` onto `addonReader.ts`, both now shared by `addonValidator` and `addonInventory`.

The next sibling, `src/c3/addonAceDiff.ts` (off-barrel; #109, capability 4), backs the read-only `diff-addon-aces` CLI subcommand + MCP tool: `diffAddonAces` diffs two `AceEntry[]` lists by `(kind, id)` identity, reporting added/removed ACEs and, for ACEs present on both sides, changed ordered `{name,type}` param signatures, rendered once via `formatAceDiff`; `resolveAceSource` sources each side via `addonReader.ts`'s `readAddonAces`, from a local `.c3addon` file path (**deliberately not** containment-guarded to `--project-dir`, unlike its read-addon/validate-addons siblings — the tool exists to diff packages living outside the project, e.g. a freshly downloaded release archive), a discovered addon id, or an extracted addon dir. It's **local-only in v1**: a remote source (a GitHub release tag/URL, fetched on the fly) is deferred to a follow-up issue — download both `.c3addon` files first and diff locally in the meantime.

The latest sibling, `src/c3/addonAceUsage.ts` (off-barrel; #110, capability 5), backs the read-only `scan-addon-usage` CLI subcommand + MCP tool: `scanAddonUsage` reports a plugin addon's **presence** (object types/families whose `plugin-id` matches, enumerated via the new shared off-barrel `src/c3/projectObjects.ts` `readProjectObjects`/`ObjectDefn` seam) and its event-sheet **ACE call sites** (conditions/actions matched on `(kind, id)` — never `objectClass`, the caller-supplied addon name — via c3source `visitEvents`), with an optional `--from` **blast-radius** mode that runs `diffAddonAces` inline and flags call sites hitting a changed/removed ACE, deliberately widening the match set to `current ∪ removed` so dangling calls to a removed ACE (the stale-reimport fallout the tool exists to catch) are still surfaced; rendered once via `formatAddonUsage` (see ADR `wiki/decisions/0010`). Its MCP tool includes the `txId` footer (it reads `eventSheets`/`objectTypes`/`families`, all tx-tracked — like `list-addons`, unlike `diff-addon-aces`), and its CLI exits 1 in blast mode only when affected call sites exist (an opt-in CI gate).

`scan-addon-usage` shipped **plugins-only** (#110), then was extended to **behavior** addons (#124, ADR `wiki/decisions/0011`): a `UsageMatcher` seam in `addonAceUsage.ts` isolates plugin-vs-behavior presence/match/attribution behind a shared event-walk + `formatAddonUsage` (ADR 0011 predicted the extension point #125 would reuse this seam for effects too). Behavior presence is keyed on `objectTypes`/`families` `behaviorTypes[]` `behaviorId` (**not** `plugin-id`); `ObjectDefn` gained an additive `behaviors: BehaviorRef[]{behaviorId,name}` (P1). The load-bearing subtlety: a call on a family **member** carries the member's own `objectClass` (not the family's) with `behaviorType` = the instance name, and is attributed to the **family** presence row while the call site keeps its real `objectClass` — a naive `objectClass ∈ hosts` predicate silently drops it. #124 also required the shared reader to **strip a UTF-8 BOM** (`addonReader.ts`): real C3-exported `.c3addon` `aces.json`/`addon.json` ship a BOM that `JSON.parse` rejects, silently emptying the ACE set for **every** addon tool — the synthetic build-archive fixtures never had one, so it stayed latent until the real behavior fixture. Discovery widened to `addons/behavior` (fixing a latent `addonLangValidator` section-key misfile). Built-in behaviors (Timer/Persist) remain unscannable by id (no bundled package → no ACE set).

`scan-addon-usage` was then extended to **effect** addons (#125, ADR `wiki/decisions/0012`) — a course-correction from ADR 0011's prediction: effects have no ACEs and no event-sheet nodes, and their application sites (layers/layouts) aren't `ObjectDefn`s, so the `UsageMatcher` seam structurally can't fit; effect support ships instead as a dedicated `scanEffectUsage` path that bypasses the event-walk shell entirely, sharing only the result types and `formatAddonUsage` rendering. Presence IS usage for an effect: the four application sites are an object type's/family's own `effectTypes[]` entry (an additive `ObjectDefn.effectTypes: EffectRef[]`) and a layout's/layer's `effectTypes[]` entry (a new `readLayoutEffects` reader in `projectObjects.ts`, since layers/layouts have no `ObjectDefn`); per-instance `effects{}` overrides are out of scope, subsumed by object-type presence. `--from` blast radius is redefined for effects — no ACE param signature to diff, so every application site is exposed by a version bump (`blast.affectedCount = effectSites.length`), and the CLI's exit-1-in-blast-mode gate fires whenever the effect is applied anywhere.

`scan-addon-usage` was finally extended to **expression usage** (#123, ADR `wiki/decisions/0015`) — the last #100 child, **closing #100**. Expressions aren't structured `(kind,id)` nodes; they live as text inside condition/action parameter strings, so a new `collectExpressionSites` pass in the event walk tokenizes every string param (c3source 1.8.0 `extractExpressionReferences`, adopted via #136) and resolves each `Object.expr`/`Object.Behavior.expr` token to an expression ACE `id` via a new `UsageMatcher.matchExpression` seam method (`findExpression` over the `readAddonAcesModel` seam). Surfaced as a parallel `expressionSites` collection + a distinct `PresenceRow.expressionSiteCount` (NOT folded into `callSiteCount`) — the `matchExpression`-on-the-seam vs separate-path call is the inverse of the #125 effect decision (expressions ride the event walk, so the seam fits; effects don't). `--from` blast flags CHANGED/REMOVED expression refs and **widens the resolution model with the diff's removed expressions** so a dangling ref to a removed expression still surfaces (the expression analogue of the removed-key match-set widening).

Capability 8 then shipped as `sync-addon-metadata` (#145) — renamed from the originally-proposed `sync-addon-version` because `author` is in scope alongside `version` — via a new off-barrel `src/c3/addonMetadataSync.ts` behind a CLI subcommand and a dual MCP-tool pair (`READ_ONLY` `preview-addon-metadata-sync`, `MUTATE` `sync-addon-metadata`): the addon cluster's **first mutation** — every prior addon tool is `READ_ONLY`. A mandatory, no-default `--direction` (`manifest-from-package` | `package-from-manifest`) names which side is source of truth — direction is a human decision the tool never infers, since C3's four-part dotted addon versions aren't semver — and only `manifest-from-package` writes; `package-from-manifest` is always a read-only report, because chef has no `.c3addon` writer. The write parses `project.c3proj` **by identity** (c3source's `readProjectManifestTolerant`), field-assigns `version`/`author` in place, and serializes via `writeProjectManifest`/`serializeProjectManifest` — never a spread, which would reorder keys and drop unmodeled fields — the same byte-fidelity discipline `projectSync.ts` already follows for its own write to the same file. See ADR `wiki/decisions/0017`.

The deferred remote-source follow-up for `diff-addon-aces` is the remaining gap.

`validate-addons` later gained `--skip-gate <families>` (#220, ADR `wiki/decisions/0038`) — a comma-delimited deny-list over its four finding families (`metadata`, `integrity`, `package-consistency`, `lang`, all four gating by default) that exempts a named family from the CLI exit code while still printing its findings; this is a narrowing of the "no severity concept" note above, and the MCP tool gets the same per-family summary line but no gate parameter, since it has no exit code to gate.
